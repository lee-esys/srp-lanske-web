# ダブルス対戦表の進行中・次対戦表示

## 目的

確定済みのダブルス対戦表で、保存されている試合状態から現在の進行対象を導出し、画面上部または対戦表表示中のフローティング操作から該当試合カードへ移動できるようにする。

実行順そのものは保存せず、対戦表の `roundNo` / `courtNo` 順を基準に判定する。

## 判定ルール

対戦表に含まれる全試合を `roundNo`、`courtNo` の順に並べ、保存済みの `ScheduleMatchProgress` を重ねる。

progress document が存在しない試合は `scheduled` とみなす。

1. `in_progress` が1件以上ある場合
   - 表示順で最初の試合を主対象とする
   - 複数件ある場合は進行中件数も表示する
2. `in_progress` がない場合
   - 表示順で最初の `scheduled` を次対戦とする
3. どちらもない場合
   - 全試合終了として扱う

後ろの試合を先に `in_progress` / `completed` にすることは禁止しない。
後ろの試合が終了して進行中試合がなくなった場合は、元の表示順で残っている最初の `scheduled` へ戻る。

判定は `schedule_progress/domain/schedule_progress_navigation.dart` の純粋なdomainロジックとして実装する。

## 進行summary

画面上部の省スペース表示は次の意味とする。

```text
終了試合数 / 全試合数
```

例:

```text
3 / 15
```

これは「現在3試合目」を意味しない。

確定済みでprogress summaryがまだ保存されていない場合は `0 / 全試合数` と表示する。
未確定の対戦表では進行summaryと進行対象表示を出さない。

## 進行対象表示

イベント情報カード内に、進行summaryとあわせて次を表示する。

- `in_progress` がある場合: 試合中
- `in_progress` がなく `scheduled` がある場合: 次の対戦
- 全試合終了時: 終了表示とページ末尾へ移動する操作
- 対象試合のラウンド
- コート表示名
- 両側の対戦者
- 対象試合へ移動する文字ラベル付き操作

複数の `in_progress` がある場合は件数を表示し、移動先は表示順で最初の試合とする。

全試合終了時は、上部の終了表示右側にも下向きアイコン付きの「終了」操作を表示し、最終対戦付近まで戻れるようにする。

表示文言は既存のFlutter l10nキーを再利用するため、Issue #147では新しいARBキーを追加しない。

## 試合カードへの移動

`ScheduleRoundsView` は各試合カードに `GlobalKey` を割り当てる。

画面上部の移動操作から主対象のkeyへ `Scrollable.ensureVisible` を実行し、該当カードまでスクロールする。

自動スクロールは常時行わず、利用者が移動操作を選んだ場合だけ実行する。

対象カードは既存の状態色を維持し、枠線を少し太くすることで控えめに強調する。

## 対戦表表示中のフローティングナビ

対戦表を下へ追っている最中に、参加者一覧やイベント情報へ簡単に戻り、再び現在／次の対戦へ戻れるようにする。

`ScheduleRoundsView` のwrapperから親 `Scrollable` の `ScrollPosition` を取得し、対戦表本体の上端が画面上部付近まで来た時点で画面下部へコンパクトなフローティングナビを表示する。

- `in_progress` がある場合
  - 「試合中」操作から主対象の試合カードへ移動する
- `in_progress` がなく `scheduled` がある場合
  - 「次の対戦」操作から主対象の試合カードへ移動する
- 全試合終了の場合
  - 下端操作でページ末尾へ移動する
- 上端操作
  - ページ先頭へ移動する

フローティングナビは画面中央ではなく右端から約40px空けて配置し、対戦表中央の視認性をできるだけ残す。

通常生成画面と共有URL復元画面はいずれも共通 `ScheduleRoundsView` を利用しているため、ページ個別のスクロール実装は追加しない。

ページ末尾に既存の80px余白を残し、最下部までスクロールした際にフローティングナビが最後の対戦カードへ重なり続けないようにする。

## Issue #161との関係

Issue #161の参加者一覧sticky表示は、「深いラウンドから参加者一覧へ戻る距離が長い」ことへの解決策として整理されている。

Issue #147のフローティングナビにより、次の往復が少ない操作で可能になる。

```text
対戦表の深い位置
  → 上端へ移動
  → 参加者確認・選択
  → 試合中 / 次の対戦へ移動
```

そのため、#161のsticky表示は#147完了後の実機運用を見て必要性を再判断する。stickyを実装する場合も、対戦表の表示領域を恒常的に狭める効果と比較する。

## 更新タイミング

### 試合結果入力後

試合保存成功時は、`DoublesMatchProgressService` が返した保存済みmatchと最新summaryを親画面のprogress snapshotへ反映する。
ダイアログ内の`baseline` / `draft`更新と並行して、背景側でも保存済みprogressを保持する。

結果入力ダイアログを閉じた後は `ScheduleRoundsView._loadProgress()` を1回実行し、progress summaryだけ最新確認する。

- summary revisionが親画面のsnapshotと同じ場合
  - 保存済みmatchesを再利用し、一覧再取得しない
- summary revisionが変わっている場合
  - matches一覧を再取得して最新状態へ揃える

この同期で次をまとめて更新する。

- 試合カードの状態・結果
- ラウンド完了表示
- `終了試合数 / 全試合数`
- 進行中／次対戦判定
- 対象カードの強調
- 画面上部／フローティングナビの移動対象

前後の試合へ移動するだけでは全体progressを再取得しない。

### 手動更新後

通常生成画面と共有URL復元画面は共通の `DoublesScheduleRefreshService` と `ScheduleRoundsView` を使用する。

手動更新では `DoublesScheduleRefreshService` が最新schedule / progressを取得し、親画面がそのsnapshotを `ScheduleRoundsView` へ渡す。
`ScheduleRoundsView` は渡されたprogressから試合カードと進行対象を再計算し、同じprogressを通信で再取得しない。

## 今回扱わないもの

- 実行順の保存・並べ替え
- 延期試合を任意位置へ差し込む機能
- 高度な試合状態
- コート空き状況からの自動割当
- 常時自動スクロール
- リアルタイム同期
- チーム対戦表への進行表示追加

チーム側の共通試合進行モデル接続はIssue #148で別途扱う。
